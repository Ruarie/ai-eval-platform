## 0. 结论摘要

### 0.1 一句话判断

平台已经完成从“评测平台”到“测试用例生成 Agent 平台”的收敛，主链路（协议档 → AgentLoop → 用例生成 → 人工审核 → 确认入库 → 导出）是通的，工程底座也明显高于一般内部工具。

下一阶段的主要矛盾**不是功能数量不够**，而是三件事：

1. **用例质量无法被证明**：需求条目没有持久化，用例没有需求追溯，AI 评审结果被覆盖，评审过程没有留痕。
2. **平台能力有骨架、缺最后一公里**：轨迹、成本、语义记忆、专家协作、媒体资产、工作区配额都已有表或代码接缝，但用户感知不到。
3. **界面与文档存在“演示态 / 历史态 / 未接入态”混杂**：登录页模拟 SSO、压测页演示数据、三个孤立路由、报告分享死代码，都会消耗用户对平台的信任。

### 0.2 五个最高优先级建议

| 顺序 | 建议 | 对应需求 | 理由 | 建议周期 |
| --- | --- | --- | --- | --- |
| 1 | 先做“说做一致”治理 | O-01、O-02、O-09、O-18 | 成本最低、信任收益最高；当前有明确的模拟入口与孤立页面 | 2 周 |
| 2 | 建立需求基线与用例追溯矩阵 | N-01 | 直接把“覆盖率”从一次性提示变成可发布门禁，是主航道最强的差异化能力 | 4–6 周 |
| 3 | 评审工作流 + 质量趋势 | N-02、N-03 | 当前 AI 评审覆盖旧结果、无评论、无版本对比；补齐后可回答“这版比上版好在哪” | 6–8 周 |
| 4 | Agent 轨迹持久化 + 成本中心 | N-09、N-10 | 已有 `harness_turns/spans` 表和 `turn_stats` 数据，属于“接线即用”的高性价比能力 | 6–8 周 |
| 5 | 技术债分批收敛 | T-01、T-02、T-05、T-07 | 新功能继续堆在 2.5k 行的 `ws.py` 和双引擎上，边际成本会越来越高 | 持续 |

### 0.3 本文明确不建议做的事项

以下事项与现行 PRD 边界冲突或缺少产品裁决，**不建议默认排期**：

- 多租户、组织/项目隔离；
- 与禅道/Jira/TMS 的双向同步；
- 自动生成可执行测试脚本并直接执行；
- 公开榜单、对外排名；
- 接入任意第三方 MCP；
- 代码题（HumanEval 等）执行族；
- 原生移动 App。

已停用的 Benchmark / RAG 评测 / 压测是否复活，必须先由 `D-01` 裁决；未裁决前只做历史只读维护，不新增执行入口。

## 1. 现状基线

### 1.1 产品与架构

```text
浏览器（Vue 3 + Naive UI）
  ├── REST /api/*
  └── WebSocket /ws/agent/v2
                │
                ▼
FastAPI API + AgentLoop v2
  ├── 认证、协议档、会话、任务、用例、知识库、工作区、报告
  ├── 工具编排、审批/澄清卡、上下文压缩、个人记忆、专家协作
  └── Worker 任务队列（当前只领取 testcase）
                │
                ▼
PostgreSQL 16 + pgvector、Redis、LightRAG（知识库）、stress（历史）
```

关键事实：

- AgentLoop v2 是唯一对话入口；旧 `ws.py` 仍保留骨架链路。
- Worker 当前只领取 `testcase`；Benchmark / RAG / stress 执行器仍在代码中，但 API 层统一拒绝新建与重跑。
- 平台是**单团队、全员同权**模型；没有 RBAC 分层，管理页对所有登录成员开放。
- 用例生成是主航道：六策略配比、分批生成、AI 对比、AI 覆盖检查、AI 评审、AI 补全、Excel/XMind 导入导出均已具备。

## 2. 问题诊断

### 2.1 P0：可信性问题（低成本、高优先）

#### P0-1 登录页提供“模拟 SSO / 社交登录”

- 现象：登录页有企业 SSO、GitHub、Telegram、Google 入口；点击后只弹提示，不发生任何认证跳转。
- 证据：`frontend/src/views/Login.vue:739-745` 的 `handleSsoLogin` 仅 `await wait(600)` 后提示“已接收接入请求”。
- 影响：用户会认为平台已支持 SSO；安全评审会把它当成真实认证面。属于典型的“演示态进入生产”。
- 建议：本期隐藏或明确标注“未接入”；若要保留入口，改为“联系管理员开通”，不得模拟成功。

#### P0-2 压测治理页用演示数据冒充真实数据

- 现象：`/admin/stress` 的“AI 容量与参数建议”写死“近 7 天峰值 QPS 462、92%、500→420”等结论，并宣称“基于近 7 天真实发压与拐点数据”。
- 证据：`frontend/src/views/AdminStress.vue:30-47`；同页还有“当前在跑数为演示值”的注释。
- 影响：该页虽未挂菜单，但可直接输入 URL 访问；一旦被当成真实治理依据，会误导容量决策。
- 建议：本期移除演示卡或改为明确的“示例/不可用”空态；若保留，必须接真实 metrics，并在无数据时显示空态。

#### P0-3 路由与导航不一致，存在三个孤立页面

- 现象：`/datasets`、`/admin/stress`、`/model-compare` 有路由、有完整页面，但侧边栏与站内没有任何入口，只能手输 URL。
- 证据：`frontend/src/router/index.ts:31,36,43`；`frontend/src/layouts/MainLayout.vue:250-266` 的 `evalRoutes/adminRoutes` 均无这三项。
- 影响：功能“存在但不可发现”；用户以为平台缺能力，维护者以为页面仍在使用。
- 建议：见 O-02，按“工作台 / 资产 / 历史评测 / 管理”重组导航；每个路由必须有入口或正式下线。

#### P0-4 契约与死代码残留

- 现象：报告分享 API 仍开放，前端仍有 `api.reports.share`，但页面没有分享入口；`ShareModal.vue`、`RagLaunchDrawer.vue`、`BenchmarkLaunchDrawer.vue`、`WorkflowDesigner.vue` 无任何引用。
- 证据：`backend/api/app/routers/reports.py:324`；`frontend/src/api/http.ts:1360`；PRD V1.52 明确“页面不再提供新的分享操作”。
- 影响：接口面大于产品面，增加安全与维护成本；新成员无法判断哪些能力仍是现行范围。
- 建议：本期二选一——恢复入口并修订 PRD，或删除前端死代码并评估是否下线 share API。不得继续保持“半开放”。

### 2.2 P1：能力缺口

| 主题 | 缺口 | 影响 | 对应需求 |
| --- | --- | --- | --- |

## 3. 需求总览与优先级

### 3.1 优先级定义

| 级别 | 定义 | 排期原则 |
| --- | --- | --- |
| P0 | 不做会误导用户、阻塞主流程或产生安全/数据风险 | 本期必须完成 |
| P1 | 显著提升主航道效率或可证明性 | 本期应完成，可按依赖排序 |
| P2 | 有价值但依赖前置或收益较慢 | 可排后 |
| D | 需要产品裁决，未裁决不排期 | 先开决策，不写代码 |

工作量单位为“人周”，是粗略量级，不含跨团队等待与真实供应商联调。

## 4. 新功能需求详述

### 4.1 N-01 需求基线与用例追溯矩阵（P0，MVP 已实现 2026-11-09）

> 已交付范围：需求基线创建/确认、用例集绑定、覆盖率与未覆盖清单、自动关联候选与人工确认；证据见 API.md V2.52 与 PRD V1.60。需求变更影响分析（N-04）仍为后续。

#### 背景与问题

当前生成链路会从需求原文抽取编号条目和硬约束（`backend/shared/casegen.py:161-166`），但只把它们拼进提示词；`CaseItem` 没有需求字段（`backend/shared/models.py:956-982`）；`/ai-coverage` 是一次性模型调用（`backend/api/app/routers/cases.py:659`），结果不留存。

直接后果：

- 无法回答“这条 FR 有没有用例”；
- 无法在确认前给出可信的覆盖率；
- 需求改版后无法判断哪些用例受影响；
- AI 评审的“覆盖度”分数没有可核对的分母。

#### 目标与成功指标

| 目标 | 指标 |
| --- | --- |
| 需求条目可持久、可校对 | 一份含 60+ 条 FR 的 PRD，抽取召回 ≥95% |
| 用例可追溯 | 生成用例自动关联需求，抽检正确率 ≥95% |
| 覆盖率可发布 | P0 需求覆盖率 100%，整体 ≥85%，缺口需显式豁免 |
| 可导出 | 追溯矩阵与缺口清单可导出 xlsx，字段可对账 |

#### 用户故事

1. 作为测试负责人，我上传 PRD 后希望先看到需求条目清单，确认无误后再生成用例。
2. 作为用例作者，我希望生成结果自动带需求编号，而不是生成完再手工补。
3. 作为评审人，我希望确认入库前看到“哪些 P0 需求没有用例”，并记录豁免原因。
4. 作为项目成员，我希望导出追溯矩阵，和产品/开发对齐范围。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 从 PRD/Markdown/Excel/OpenAPI 文本中抽取需求条目：编号、标题、优先级、模块、原文位置、原文摘要 | P0 |
| FR-2 | 抽取结果可人工编辑、合并、拆分、忽略；确认后形成需求基线 | P0 |
| FR-3 | 需求基线版本化；用例集记录生成时使用的基线版本，后续基线变更不回溯影响旧集 | P0 |
| FR-4 | 用例生成时自动填 `requirement_ids`；保存/编辑时校验引用有效 | P0 |
| FR-5 | 支持手工关联/取消关联；一条用例可关联多条需求 | P1 |
| FR-6 | 覆盖率计算：按需求条目统计用例数、策略分布、P0/P1/P2 覆盖；区分“无用例”“仅正向用例”“仅 AI 判定覆盖” | P0 |
| FR-7 | 覆盖率看板：整体/模块/优先级、未覆盖 Top N、P0 缺口、趋势 | P1 |
| FR-8 | 确认入库门禁：P0 缺口必须显式豁免并填写原因；不默认硬阻断 | P0 |
| FR-9 | 导出追溯矩阵、缺口清单、豁免记录 | P1 |
| FR-10 | 权限沿用全员同权；所有基线确认、关联变更、豁免写审计 | P0 |

#### 规则与边界

- 需求条目必须来自原文，不允许模型臆造；模型只做结构化，不做扩写。
- 未确认的需求条目不进入覆盖率分母。
- 用例确认后仍是只读快照；补关联必须通过 N-02 的版本机制产生新草稿，不直接改历史。
- 需求基线确认后不可原地修改；修订生成新版本，旧版本只读。
- 覆盖率是“可证明的覆盖”，不宣称“功能正确”；页面文案必须区分“有用例”和“已验证”。

#### 数据与接口影响

| 项 | 建议 |
| --- | --- |
| 新表 | `requirement_baselines`（版本、来源、状态、创建者）、`requirements`（条目、优先级、模块、原文位置）、`case_requirement_links`（用例 ID、需求 ID、来源、置信度） |

3. P0 缺口未豁免时，确认按钮给出明确阻断/确认文案；豁免后审计可查。

5. 现有生成/确认/导出流程无回归；1 万条用例的覆盖率查询 P95 <300ms。

### 4.2 N-02 用例评审工作流与版本历史（P0）

#### 背景与问题

`CaseSet` 只有 `generated/confirmed/cancelled` 三个状态（`backend/shared/models.py:929-934`），确认后只读；保存靠 `revision` 乐观锁；AI 评审结果写入 `case_sets.checks` 时**覆盖旧评审**（`backend/api/app/routers/cases.py:988-993`）。没有评论、没有版本 diff、没有评审结论。

直接后果：

- 评审意见散落在聊天工具里，平台内不可追溯；
- 无法回答“这版改了哪些用例、为什么改”；
- AI 评审分数无法形成趋势，无法比较模型/提示词版本；
- 多人评审时只有“保存冲突”，没有协作语义。

#### 目标与成功指标

| 目标 | 指标 |
| --- | --- |
| 评审过程留痕 | 每次评审有指派人、结论、意见、时间 |
| 版本可对比 | 任意两个版本可字段级 diff |
| AI 评审可追溯 | 保留每次评分与问题清单，可按时间对比 |
| 不破坏现有确认链路 | 72h 确认、任务联动、只读快照行为不变 |

#### 用户故事

1. 作为用例作者，我提交评审后能看到谁在评审、提了什么意见。
2. 作为评审人，我能逐条评论，也能给出“通过/驳回/有条件通过”。
3. 作为负责人，我能看到两个版本的差异，并决定是否回滚。
4. 作为质量负责人，我能看到同一用例集多轮 AI 评审的分数变化。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 新增独立 `review_state`（`draft/reviewing/changes_requested/approved`），**不扩展** `CaseSet.status`，避免破坏 CHECK 约束与任务联动 | P0 |
| FR-2 | 评审指派/自领、截止时间、评审人列表 | P0 |
| FR-3 | 整体评论 + 用例行级评论；支持 @成员 | P1 |
| FR-4 | 版本快照：每次确认、每次显式“存为版本”生成不可变快照 | P0 |
| FR-5 | 版本 diff：字段级新增/删除/修改；支持并排查看 | P0 |
| FR-6 | 回滚：以历史版本创建新草稿，不覆盖历史 | P1 |
| FR-7 | AI 评审历史：每次评分、四维分、问题清单、模型/提示词版本、耗时 | P0 |
| FR-8 | 评审结论：通过/驳回/有条件通过；驳回必须填原因 | P0 |
| FR-9 | 确认门禁：`review_state=approved` 才允许确认；紧急情况可显式豁免并审计 | P0 |
| FR-10 | 评审事件通知（依赖 N-08） | P1 |
| FR-11 | 评审历史导出（CSV/JSON） | P2 |

#### 规则与边界

- 已确认用例集仍是只读快照；回滚产生新草稿，不修改历史。
- 评审意见只能追加更正，不能物理删除；删除走“撤回 + 保留审计”。
- 评审不改变用例内容；编辑仍走现有保存接口与 `revision` 冲突。
- 不把 `status` 改成多态状态机；避免影响 `awaiting_case_confirm`、72h 超时、任务取消联动。
- 全员同权不变；评审人是操作身份，不是权限等级。

#### 数据与接口影响

| 项 | 建议 |
| --- | --- |
| 新表 | `case_set_versions`、`case_item_versions`（可存 JSON 快照）、`case_reviews`、`case_review_comments`、`case_review_runs`（AI） |
| 字段 | `case_sets.review_state`、`case_sets.current_version_id` |
| REST | `POST /api/case-sets/{id}/reviews`、`POST /api/case-sets/{id}/reviews/{rid}/comments`、`GET /api/case-sets/{id}/versions`、`GET /api/case-sets/{id}/versions/{v}/diff`、`POST /api/case-sets/{id}/versions/{v}/restore` |

#### 验收标准

1. 两名成员同时评审同一用例集，意见不丢失、不覆盖。
2. 两个版本的 diff 能准确显示字段变化；回滚后原版本仍可查。
3. 连续三次 AI 评审均保留，页面可按时间查看分数与问题。

### 4.3 N-03 生成与评审质量趋势（P1）

#### 背景与问题

`CaseSet` 已有 `generated_count` 与 `confirmed_count`，可算单集采纳率；但没有生成批次记录、没有跨集趋势、AI 评审覆盖旧值（见 N-02）。PRD 把“用例采纳率 ≥70%”列为成功指标，但目前没有可核对的看板。

#### 目标

- 记录每次生成运行：模型、提示词版本、策略配比、目标/实际条数、耗时、token、失败原因。
- 聚合质量指标：采纳率、确认率、AI 四维分、待补全率、重复率、人工修改率。
- 支持按周、模型、需求模块对比；异常可告警。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 生成运行记录：任务 ID、用例集 ID、模型/协议档、提示词/技能版本、策略配比、目标条数、实际条数、耗时、token、状态 | P0 |
| FR-2 | 单集指标：采纳率、确认率、AI 四维分、待补全率、重复率 | P0 |
| FR-3 | 跨集趋势：按周/月、模型、模块、策略 | P0 |
| FR-4 | 人工修改率：保存前后字段 diff 统计（依赖 N-02 版本） | P1 |
| FR-5 | 异常清单：空输出、截断、解析失败、覆盖率下降、确认超时 | P1 |
| FR-6 | 导出 CSV 与看板截图式报告 | P2 |
| FR-7 | 口径说明：每个指标给出计算公式与分母，禁止无分母百分比 | P0 |

#### 规则与边界

- 指标只统计真实落库数据；失败任务不伪装成 0 条成功。
- 采纳率 = 确认入库条数 / 当次生成条数；人工新增不计入分母，单独展示。
- AI 评分不作为质量唯一依据；必须与采纳率、人工修改率并列。
- 模型/提示词版本变化要标记，避免把版本差异误判为能力差异。

#### 数据与接口影响

- 新表 `casegen_runs`；必要时 `casegen_run_sections` 记录分批。
- REST：`GET /api/casegen/metrics?range=&group_by=`、`GET /api/casegen/runs`。
- 指标可先离线聚合，后续再做物化视图；避免在列表接口实时全表扫描。

#### 验收标准

1. 看板数字与任务/用例集明细逐条对账一致。
2. 同一份需求重复生成 3 次，趋势图显示 3 个点，模型/配置可区分。
3. 失败任务显示失败原因，不计入成功率分母的方式有明确说明。
4. 30 天范围查询 P95 <500ms。

#### 预估

3–4 人周（后端 2、前端 2）。

### 4.4 N-04 需求变更影响分析（P1）

#### 背景与问题

需求改版是用例维护的最大成本来源。当前没有需求基线（N-01），因此无法做 diff，也无法知道哪些用例需要改。

#### 目标

- 上传需求新版本，自动对比条目新增/修改/删除。
- 列出受影响用例与覆盖变化。
- 经人工确认后，批量创建“变更处理”草稿，不直接修改已确认集。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 新版本需求上传，自动匹配同一基线并生成 diff | P0 |
| FR-2 | diff 分类：新增、修改（字段级）、删除、优先级变化、模块移动 | P0 |
| FR-3 | 影响分析：关联用例列表、覆盖变化、建议动作（新增/修改/废弃） | P0 |
| FR-4 | 人工确认后批量创建新草稿；保留变更来源与基线版本 | P0 |
| FR-5 | 变更报告导出 | P1 |
| FR-6 | 不自动删除旧用例；废弃需人工确认 | P0 |

#### 规则

- 匹配以需求编号优先，其次标题+模块相似度；低置信度必须人工确认。
- 变更分析不直接改已确认用例集；生成新草稿并走 N-02 评审。
- 删除的需求只标记“待废弃”，不物理删除历史用例。

#### 验收标准

1. 修改一条 FR 的描述，能准确列出关联用例，不误报无关用例。
2. 新增 5 条 FR，能生成 5 条“未覆盖”提示。
3. 批量创建草稿后，来源、基线版本、变更原因可查。
4. 对 500 条需求、5000 条用例，分析在 2 分钟内完成。

#### 预估

4–5 人周（后端 3、前端 2）。

### 4.5 N-05 团队用例资产库与语义去重（P1）

#### 背景与问题

用例只存在于各用例集的 `case_items` 中；确认后的用例集是快照。没有跨集检索、标签、去重、引用。结果是同一业务规则被反复生成、反复评审。

平台已有可选 Embedding 协议档与 pgvector，具备做语义去重的条件。

#### 目标

- 建立跨用例集的团队用例资产库。
- 支持标签、搜索、相似提示、合并、引用/克隆。
- 去重必须人工确认，可撤销。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 用例确认入库时物化到资产库（保留来源集、版本、作者） | P0 |
| FR-2 | 资产库列表：模块、策略、优先级、标签、文本、来源、时间筛选 | P0 |
| FR-3 | 自定义标签与批量打标 | P1 |
| FR-4 | 文本相似 + 向量相似去重提示；阈值可配 | P0 |
| FR-5 | 合并/保留/忽略；合并保留历史与来源，可撤销 | P0 |
| FR-6 | 从资产库引用或克隆到当前草稿 | P1 |
| FR-7 | 质量标记：已验证、常用、过期、待复核 | P2 |
| FR-8 | 资产统计：模块分布、重复率、复用次数 | P2 |
| FR-9 | 权限：全员可读；编辑/合并记录操作者与审计 | P0 |

#### 规则

- 资产库的“已验证”只代表人工标记，不代表平台自动证明正确。
- 语义去重只做提示，不自动删除或合并。
- 引用与克隆必须保留来源；删除来源集不影响资产快照。
- 向量模型不可用时降级为文本相似，并明确标注“未使用语义”。

#### 数据与接口影响

- 新表 `case_assets`、`case_asset_tags`、`case_asset_links`；`embedding` 用 pgvector，维度按选定模型固定（切换模型需重建索引）。
- REST：`GET /api/case-assets`、`POST /api/case-assets/{id}/tags`、`POST /api/case-assets/merge`、`POST /api/case-assets/{id}/clone`。
- 写入时机：确认入库事务内物化，失败不影响确认主流程（可补偿）。

#### 验收标准

1. 1 万条资产按模块/标签/文本检索 P95 <500ms。
2. 相似提示抽检 20 组，准确 ≥16 组；误报可一键忽略。
3. 合并后来源、历史、用例数可查；撤销恢复原状。
4. 关闭 embedding 时功能可用，页面明确标注“文本相似”。

#### 依赖与风险

- 依赖：N-01/N-02 的稳定数据；embedding 协议档需可用。
- 风险：误合并；向量成本；资产库与用例集快照不一致。
- 缓解：人工确认、可撤销、来源追踪、确认事务内物化。

#### 预估

6–8 人周（后端 4、前端 3、测试 1）。

### 4.6 N-06 用例执行记录与质量回流（P2，需裁决）

> 这是**新增产品范围**。PRD 当前明确“用例不同步 TMS、不生成可执行脚本”，但没有禁止“平台内手工执行记录”。是否纳入，需 `D-03` 裁决。

#### 背景

用例生成后，平台不知道它们是否被执行、是否发现缺陷。没有执行数据，“用例质量”只能靠 AI 评分与人工采纳，缺少最终验证。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 以“执行轮次”组织：选择用例集版本、环境、执行人、时间 | P0 |
| FR-2 | 逐条记录结果：通过/失败/阻塞/跳过/未执行 | P0 |
| FR-3 | 失败证据：截图/日志附件、备注、缺陷编号（自由文本，不接 TMS） | P1 |
| FR-4 | 统计：通过率、阻塞率、缺陷密度、按模块/优先级分布 | P0 |
| FR-5 | 失败用例一键生成“复测草稿”或“补充用例草稿” | P2 |
| FR-6 | 标记不稳定用例（flaky），供后续生成参考 | P2 |
| FR-7 | 导出执行报告 | P1 |

#### 规则

- 只记录人工执行结果；不自动执行脚本、不接外部 TMS。
- 执行记录不修改用例快照；结果关联版本。
- 失败证据属于平台文件资产，遵循文件权限与保留策略。

#### 验收标准

1. 100 条用例的单轮执行记录可在 5 分钟内完成。
2. 统计与明细一致；导出可打开。
3. 执行记录不改变已确认用例内容。
4. 审计可查谁在何时改过结果。

#### 预估

6–8 人周。

### 4.9 N-09 Agent 轨迹持久化与诊断（P1）

#### 背景与问题

前端已有 `TraceWorkspace`，能展示模型请求、工具执行、事件详情（`frontend/src/components/agent/loop/TraceWorkspace.vue`），但它依赖当前会话的 `LoopState`，刷新或重启即丢。数据库里 `harness_turns`、`harness_spans`、`harness_diagnostics` 已建表，但全仓没有写入方（`backend/shared/models.py:1121-1155`）。

#### 目标

- 每轮对话可持久回放，刷新/重启后仍可查。
- 能回答“慢在哪、失败在哪、审批等了多久”。
- 支持按会话、用户、模型、工具、状态检索。
- 默认不存敏感内容，可配置脱敏级别。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 写入 Turn：会话、用户、专家、模型、协议档、开始/结束、耗时、token | P0 |
| FR-2 | 写入 Span：模型调用、工具调用、审批等待、压缩、记忆召回 | P0 |
| FR-3 | 记录状态与错误码；错误摘要脱敏 | P0 |
| FR-4 | 查询 API：按会话/时间/模型/工具/错误码分页 | P0 |
| FR-5 | 前端轨迹回放：复用 `TraceWorkspace`，支持跨会话打开 | P0 |
| FR-6 | 慢 Span Top N、工具失败率、审批等待分布 | P1 |
| FR-7 | 两轮对比：同问题不同模型/提示词版本 | P2 |
| FR-8 | 导出 JSON（脱敏） | P1 |
| FR-9 | 保留与清理：默认 30 天，可配置 | P0 |
| FR-10 | 权限：会话属主、管理员、团队会话协作者按现有规则 | P0 |

#### 规则

- 默认不持久化完整提示词、工具大结果、图片 base64；只存摘要、hash、长度、耗时。
- 诊断 traceback 仅服务端可见，API 只返回安全错误码与摘要。
- 轨迹写入失败不阻断对话；记录降级日志。
- 轨迹不是审计替代品；审计仍以 `audit_logs` 为准。

#### 数据与接口影响

- 激活 `harness_turns/spans/diagnostics`；补索引（session_id, created_at）、（model, status）。
- REST：`GET /api/sessions/{id}/turns`、`GET /api/turns/{id}/spans`、`GET /api/diagnostics?range=`。
- 写入在 AgentLoop 收尾与工具调度处，异步批量写入，避免阻塞流式。

#### 验收标准

1. 刷新页面、重启 API 后，历史轮次轨迹仍可打开。
2. 1 万 Span 查询 P95 <1s；分页稳定。
3. 默认导出不含提示词正文、密钥、完整工具结果。
4. 轨迹写入失败时对话仍成功，且有降级指标。

#### 依赖与风险

- 依赖：T-07 明确未使用表是保留还是删除。
- 风险：写放大、存储增长、隐私泄漏。
- 缓解：采样（成功轮次可采样，失败轮次全量）、TTL、脱敏、异步写。

#### 预估

6–8 人周。

### 4.10 N-10 用量与成本中心（P1）

#### 背景与问题

每条 assistant 消息已有 `turn_stats`（模型轮数、token、工具成败），见 `backend/shared/models.py:222-224`；`usage_ledger` 只在 benchmark 写入，API 不读。平台没有价格表、没有按用户/会话/模型的成本聚合，无法回答“一次用例集要多少钱”。

#### 目标

- 建立模型价格表与成本估算口径。
- 按日/用户/会话/模型/协议档聚合 token 与费用。
- 支持预算阈值告警；是否硬停由 `D-08` 裁决。
- 未知用量明确标注，不用 0 冒充。

#### 功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-1 | 价格表：按 profile/model 配置输入/输出/缓存 token 单价与币种 | P0 |
| FR-2 | 聚合：输入/输出/推理/缓存 token、调用次数、估算费用 | P0 |
| FR-3 | 维度：日、用户、会话、模型、协议档、工作区 | P0 |
| FR-4 | 预算：用户/会话/月度阈值；告警；可选硬停 | P1 |
| FR-5 | 归因：消息、轮次、任务、用例集 | P1 |
| FR-6 | 价格快照：历史费用不因改价重算 | P0 |
| FR-7 | 未知用量、缺失价格、失败调用单独统计 | P0 |
| FR-8 | 导出 CSV | P1 |
| FR-9 | 管理端价格维护与审计 | P0 |

#### 规则

- 费用是估算值，页面必须标注“估算”，不得作为财务结算依据。
- 供应商未返回 usage 时标记 unknown，不按字符数猜算。
- 价格变更只影响之后发生的调用；历史按快照。
- 预算硬停必须可配置默认关闭，避免误伤长任务。

#### 数据与接口影响

- 新表 `model_prices`、`agent_usage_daily`（或物化视图）；`usage_ledger` 可扩展 `session_id` 但建议新表，避免任务语义污染。
- REST：`GET /api/usage/summary`、`GET /api/usage/series`、`GET/PUT /api/admin/model-prices`。
- 聚合任务由 Worker 定时跑，API 只读汇总。

#### 验收标准

1. 汇总与 `turn_stats` 逐条求和在 1% 误差内（四舍五入除外）。
2. 30 天、10 万条消息查询 P95 <1s。
3. 改价后历史金额不变。
4. 未知用量占比可见，且不会被算成 0。

#### 预估

4–6 人周。

## 10. 交付规范

### 10.1 单条需求 DoD

一条需求只有同时满足以下条件才算完成：

1. PRD/API.md 已更新，字段、错误码、权限边界明确；
2. 数据库变更由 Alembic 迁移管理，含 upgrade/downgrade 或向后兼容说明；
3. 后端单测 + 契约测试，前端组件测试 + 关键 e2e；
4. 错误态、空态、加载态完整；无 `except Exception` 直接回显原文；
5. 无密钥、Cookie、完整提示词进入日志/响应/通知；
6. 有可观测指标（至少日志 + 一个计数/耗时）；
7. 有回滚或关闭开关（高风险功能默认关闭）；
8. 文档附“修改文件与作用清单”；
9. 通过本地门禁：`ruff + pytest`、Worker `pytest`、前端 `typecheck + build`。

### 10.2 契约与迁移门禁

- 新增 REST/WS 字段：先改 API.md，再改代码；前端类型同步。
- 新增表/字段：先迁移，再写模型；禁止手改生产库。
- 修改状态机/枚举：必须评估旧数据兼容与 CHECK 约束；优先新增字段而非扩展旧枚举。
- 外部协议/供应商字段：必须有夹具单测与真实探活证据。

### 10.3 发布与回滚

- 高风险功能（语义记忆、后台运行、媒体、开放 API、权限）必须有 feature flag，默认关闭。
- 发布前跑 smoke：登录、Agent 对话、用例生成、确认、导出、任务取消、工作区读写。
- 回滚：应用镜像回滚 + 迁移兼容；禁止依赖“删表回滚”。
- 发布后 24 小时观察：错误率、队列深度、P95、成本异常。
